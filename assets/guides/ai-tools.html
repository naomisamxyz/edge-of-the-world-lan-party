Chatbots

    
Chat models such as ChatGPT, Claude, and Gemini can help you think through a game before you begin coding. They are useful as a patient tutor and sounding board for developing mechanics, planning a project, understanding errors, and working through unfamiliar syntax.


    
What they are good at

    
    
      
  • Developing a game mechanic and identifying the objects, components, variables, events, and scripts it might require.
    • 
      
  • Planning how a project should be organized before writing any code.
    • 
      
  • Explaining compiler errors and Unity Console messages in plain language.
    • 
      
  • Turning an idea such as “open the door when the player is nearby” into a Unity approach you can build and test.
    • 
      
  • Reviewing a short script you wrote and identifying likely problems or unclear sections.
    • 
      
  • Summarizing documentation or drafting simple boilerplate that you will inspect, test, and revise.
    • 
    


    
Asking well

    
Include the complete error message, the relevant code, your Unity version, and a short description of the GameObjects and components involved. Explain what you expected to happen and what happened instead. Specific context produces more useful answers; vague questions produce guesses.


    
Where they break

    
    
      
  • They can confidently invent methods, components, settings, and menu paths. Verify unfamiliar API names in the Unity Scripting Reference.
    • 
      
  • They cannot see your scene, component settings, file structure, or scripts unless you provide that information. Anything missing from the prompt is an assumption.
    • 
      
  • Long conversations lose focus and accumulate incorrect assumptions. Start a new conversation for each distinct problem and restate the relevant context.
    • 
    


    
Protect the project

    
It is not safe to give an AI coding agent direct access to a Unity project. Every time you change a script or ask AI to generate or revise code, first save the last working version somewhere outside the live Unity project, or preserve it with version control.

    
Do not keep duplicate .cs script files inside the project as backups. Unity will try to compile every script in the Assets folder, and duplicate classes or old code can cause errors. Keep backups outside the project instead.

  


  

  

    
Generating assets

    
Generative tools can produce 3D models, textures, sprites, sound, and music from a text prompt or an image. Treat the output as raw material, not finished work.


    
    
      
  • 3D models: Meshy, Tripo, and Rodin do text-to-mesh or image-to-mesh. Expect messy topology and lighting baked into the texture. Good for blockouts, background props, and anything you plan to retexture.
    • 
      
  • Textures, sprites, concept art: image generators, plus texture-specific tools. Watch for seams that do not tile and style that drifts across a set.
    • 
      
  • Audio: tools exist for sound effects and for music beds. Check the licence before you ship anything.
    • 
      
  • Animation: Mixamo for auto-rigging and a motion library (not generative), and video-to-mocap tools such as DeepMotion.
    • 
    


    
Getting it into Unity

    
Import models as FBX or glTF, keep one Unity unit as one metre, and move files inside Unity so their .meta links survive (see First Project Setup and Unity Best Practice).

  


  

  

    
AI-assisted workflows

    
Every tool shapes how you understand what you are working on, not only what you can build with it. Tools also have politics: who owns them, whose labor and data built them, how much energy they use, what happens to the material you give them, and who benefits.


    
Learning to code has always involved searching for solutions, reading documentation, finding code that someone shared, taking it apart, changing it, and learning how it works in your own project. AI can accelerate that process by helping you develop an idea, locate possible approaches, explain unfamiliar code, and debug problems.

    
AI can help write code, but you still need enough understanding to know what to ask for, where the code belongs, what it changes, how it connects to the rest of the project, and when the result is wrong. Treat it as a collaborator that needs clear boundaries, complete context, and close supervision.


    
A controlled workflow

    
    
      
  • 
        
    Intention + boundaries
    
        
    Explain what you are trying to build, limit the scope, and say how you want to work. Ask for one understandable step at a time and require permission before any change.
    
        
    “I'm building a simple Unity interaction where clicking an object changes its material. I want to build this one step at a time using basic C# that I can understand. Start by helping me detect when the object is clicked. Don't write the material-changing part yet. Always ask for my permission before making changes. Only do what I ask, and keep your answers short and precise.”
    
      
    • 
      
  • 
        
    Give it your input
    
        
    Provide the relevant script, exact error, component setup, and other context. Let it understand what already exists before proposing changes.
    
        
    “Here is my current script. Read it and explain how it works. Don't change or rewrite anything yet.”
    
      
    • 
      
  • 
        
    Give exact instructions + approach
    
        
    Describe precisely what should change. If you are practicing a particular concept, require the solution to use it and prohibit unnecessary systems.
    
        
    “Change the script so clicking the object switches between two materials. Use a bool to track which material is active and an if / else statement to decide which material to apply. Store both materials as public variables so I can assign them in the Unity Inspector. Keep the code simple and don't introduce additional systems or concepts.”
    
      
    • 
      
  • 
        
    Repeat back
    
        
    Before any code is written, make sure the tool understood both the task and its limits.
    
        
    “Before you do anything, repeat what you understood and how you are going to approach it.”
    
      
    • 
      
  • 
        
    Execute
    
        
    Correct the plan if necessary, save the last working version, and then authorize only the specific step you discussed.
    
        
    “Only make the changes we agreed on. Don't change anything else.”
    
      
    • 
      
  • 
        
    Test + debug
    
        
    Run the change in Unity. If it fails, report the exact error and observed behavior. Diagnose one possibility at a time before changing more code.
    
        
    “The material isn't changing when I click. There are no errors in the Console. Help me identify the cause. Let's test one thing at a time, and don't change the code until we know what is wrong.”
