Don’t Destroy on Load

    
Normally, Unity destroys the objects in the current scene when another scene loads. DontDestroyOnLoad allows one object to survive.

    
Create the object in the first scene—or as early as possible—and keep it at the top level of the Hierarchy.


    
Option A: Visual Scripting

    
Add a Script Machine component to the object and create a Script Graph:

    
On Start ───▶ Don’t Destroy on Load
                    ▲
                   Self

    
Connect Self to the target input.


    
Option B: C#

    
Add this script to the object:

    
using UnityEngine;

public class KeepAlive : MonoBehaviour
{
    void Awake()
    {
        // Keep this GameObject alive when Unity loads another scene.
        DontDestroyOnLoad(gameObject);
    }
}

    
Load another scene. The object should remain in the Hierarchy.

State tracking

    
A state is a piece of information that describes the game at a particular moment.

    
Different variable types can track different kinds of state:

    
    
      
  • An int can track health, currency or collected objects.
    • 
      
  • A float can track time, distance or energy.
    • 
      
  • A bool can record whether something has happened.
    • 
      
  • A string can store a name, message or location.
    • 
      
  • A list can hold items, objectives or discovered places.
    • 
    

    
State tracking allows an action in one scene to have consequences in another.

Option A: Visual Scripting

    
What is an Application Variable?

    
An Application Variable is a value stored globally by Unity Visual Scripting.

    
Application Variables:

    
    
      
  • Can be accessed by different Script Graphs.
    • 
      
  • Remain available when the scene changes.
    • 
      
  • Last for the current play session.
    • 
      
  • Reset when the game closes or Play Mode stops.
    • 
    

    
They provide Visual Scripting with a simple place to store health, scores, inventory and other shared information.

    
Create them through the Application section of the Visual Scripting Variables window or Blackboard.

    
A Saved Variable is different: it can preserve simple values after the game closes.

Option B: C#

    
Create the GameState

    
Create an empty GameObject named GameState in the first scene and add this script:

    
using TMPro;
using UnityEngine;

public class GameState : MonoBehaviour
{
    // The number of objects the player has collected.
    public int collectedObjects = 0;

    // Optional TextMeshPro display.
    public TMP_Text stateText;

    void Awake()
    {
        // Keep GameState and its children between scenes.
        DontDestroyOnLoad(gameObject);
    }

    void Start()
    {
        // Display the starting value.
        UpdateDisplay();
    }

    public void CollectObject()
    {
        // Increase the counter by one.
        collectedObjects++;

        // Display the new value in the Unity Console.
        Debug.Log("Collected objects: " + collectedObjects);

        // Update the Canvas.
        UpdateDisplay();
    }

    void UpdateDisplay()
    {
        // Only update the Canvas if a Text object was assigned.
        if (stateText != null)
        {
            stateText.text = "Collected: " + collectedObjects;
        }
    }
}

    
Create a Canvas display

    
    
      
  1. Create a Canvas as a child of GameState.
    2. 
      
  2. Add a TextMeshPro Text object.
    3. 
      
  3. Drag the Text object into the State Text field on GameState.
    4. 
    

    
Because the Canvas is a child of GameState, it also survives scene changes.

    
Why does the C# version use two scripts?

    
The C# examples separate two responsibilities:

    
    
      
  • GameState stores the information.
    • 
      
  • Collectible or InventoryItem reports that something was collected.
    • 
    

    
The Visual Scripting examples use Application Variables for storage, so the collectible graph can change the shared value directly.

    
A single collectible graph can be reused on many collectible objects. It does not require a different graph for every item.

    
Create the collectible

    
Add this script to a collectible:

    
using UnityEngine;
using UnityEngine.EventSystems;

public class Collectible : MonoBehaviour, IPointerClickHandler
{
    // Unity calls this method when the player clicks the object.
    public void OnPointerClick(PointerEventData eventData)
    {
        // Find the persistent GameState object.
        GameState state = FindFirstObjectByType<GameState>();

        // Tell GameState that an object was collected.
        state.CollectObject();

        // Remove this collectible from the scene.
        Destroy(gameObject);
    }
}

    
Add a Collider to the collectible. Enter Play Mode and click it.

    
The value will appear:

    
    
      
  • In the Unity Console.
    • 
      
  • On the Canvas.
    • 
      
  • In the GameState Inspector.

Inventory systems

    
An inventory is a collection of state. It records which objects the player currently owns.

    
A complete inventory might track:

    
    
      
  • Item names
    • 
      
  • Quantities
    • 
      
  • Images or icons
    • 
      
  • Descriptions
    • 
      
  • Categories
    • 
      
  • Item effects
    • 
      
  • Whether an item has been used
    • 
    

    
The simplest inventory can be a list of item names.


    
Option A: Visual Scripting

    
Create the inventory variables

    
Create two Application Variables:

    
Name: Inventory
Type: List of Strings
Starting value: Empty List

    
Name: InventoryDisplay
Type: String
Starting value: ""

Option B: C#

    
Expand GameState so it can hold an inventory:

    
using System.Collections.Generic;
using TMPro;
using UnityEngine;

public class GameState : MonoBehaviour
{
    // Countable game state.
    public int collectedObjects = 0;

    // A simple inventory containing item names.
    public List<string> inventory = new List<string>();

    // Optional TextMeshPro display.
    public TMP_Text stateText;

    void Awake()
    {
        // Keep GameState and its children between scenes.
        DontDestroyOnLoad(gameObject);
    }

    void Start()
    {
        // Display the starting state.
        UpdateDisplay();
    }

    public void CollectObject()
    {
        // Increase the collection counter.
        collectedObjects++;

        // Report the change in the Console.
        Debug.Log("Collected objects: " + collectedObjects);

        // Refresh the Canvas text.
        UpdateDisplay();
    }

    public void AddItem(string itemName)
    {
        // Add the item's name to the inventory list.
        inventory.Add(itemName);

        // Report the newly collected item.
        Debug.Log("Added to inventory: " + itemName);

        // Show the complete inventory in the Console.
        Debug.Log("Inventory: " + string.Join(", ", inventory));

        // Refresh the Canvas text.
        UpdateDisplay();
    }

    void UpdateDisplay()
    {
        // Stop if no Text object was assigned.
        if (stateText == null)
        {
            return;
        }

        // Put every inventory item on a separate line.
        string inventoryList = string.Join("\n", inventory);

        // Display the counter and complete inventory.
        stateText.text =
            "Collected: " + collectedObjects +
            "\n\nInventory:\n" + inventoryList;
    }
}

    
Add this script to an inventory item:

    
using UnityEngine;
using UnityEngine.EventSystems;

public class InventoryItem : MonoBehaviour, IPointerClickHandler
{
    // Change this name for each inventory object.
    public string itemName = "Key";

    // Unity calls this method when the player clicks the object.
    public void OnPointerClick(PointerEventData eventData)
    {
        // Find the persistent GameState.
        GameState state = FindFirstObjectByType<GameState>();

        // Add this item's name to the inventory.
        state.AddItem(itemName);

        // Remove the physical object from the scene.
        Destroy(gameObject);
    }
}

    
Add a Collider to the item. Change Item Name in the Inspector for each object.

Scriptable Objects

    
Strings are suitable for a first experiment, but larger inventories need more information. A Scriptable Object is an asset that stores information outside of any scene.

    
A Scriptable Object can define:

    
    
      
  • Item name
    • 
      
  • Icon
    • 
      
  • Description
    • 
      
  • Value
    • 
      
  • Category
    • 
      
  • Possible actions
    • 
      
  • Sound and visual effects
    • 
    

    
Several objects can reference the same Scriptable Object instead of duplicating the information in every scene.

    
Scriptable Objects define what an item is. GameState or an Application Variable records whether the player owns it.


    
Create an item asset

    
Scriptable Objects are defined with a short C# script. Visual Scripting graphs can read their values, but the asset type itself is written in C#.

    
using UnityEngine;

// Creates an "Item" entry in the Create menu.
[CreateAssetMenu(fileName = "NewItem", menuName = "Inventory/Item")]
public class ItemData : ScriptableObject
{
    public string itemName;
    public Sprite icon;

    [TextArea]
    public string description;
}

    
    
      
  1. Save the script as ItemData.
    2. 
      
  2. In the Project window, choose Create → Inventory → Item.
    3. 
      
  3. Name the asset Key. In the Inspector, fill in its name, icon and description.
    4. 
      
  4. Duplicate the asset for each other item: Letter, Medicine, Photograph and Tool.
    5. 
    


    
Use the asset in the inventory

    
Change InventoryItem so it holds an Item asset instead of a typed name:

    
using UnityEngine;
using UnityEngine.EventSystems;

public class InventoryItem : MonoBehaviour, IPointerClickHandler
{
    // Drag an Item asset here instead of typing a name.
    public ItemData item;

    // Unity calls this method when the player clicks the object.
    public void OnPointerClick(PointerEventData eventData)
    {
        // Find the persistent GameState.
        GameState state = FindFirstObjectByType<GameState>();

        // Add the asset's name to the inventory.
        state.AddItem(item.itemName);

        // Remove the physical object from the scene.
        Destroy(gameObject);
    }
}

    
Drag the matching Item asset into the Item field on each collectible object. Several objects can use the same asset.

    
The inventory still records only the item’s name. The asset supplies everything else, so an icon or description can be shown whenever it is needed.

    
Scriptable Objects do not automatically save the player’s progress after the game closes.

  


  

    
Object pooling

    
Object pooling is useful when objects are created and destroyed repeatedly:

    
    
      
  • Projectiles
    • 
      
  • Enemies
    • 
      
  • Particle effects
    • 
      
  • Collectible visuals
    • 
      
  • Repeating environmental objects
    • 
    

    
Creating and destroying objects again and again is slow. A pool creates a set of objects once, keeps the unused ones hidden, and reuses them.


    
Option A: Visual Scripting

    
The basic habit is to hide an object instead of destroying it:

    
Set Active
Value: False
Target: Self

    
Use Set Active with Value True to bring it back later. A complete pool in a graph needs a List variable and a loop, which is much easier in C#.


    
Option B: C#

    
Hide the object instead of destroying it:

    
// Hide the object so it can be reused later.
gameObject.SetActive(false);

    
A simple pool creates the copies once and reuses them:

    
using System.Collections.Generic;
using UnityEngine;

public class SimplePool : MonoBehaviour
{
    // The object to reuse, for example a small sphere prefab.
    public GameObject prefab;

    // How many copies to create at the start.
    public int poolSize = 10;

    List<GameObject> pool = new List<GameObject>();

    void Start()
    {
        // Create every copy once and hide it.
        for (int i = 0; i < poolSize; i++)
        {
            GameObject copy = Instantiate(prefab, transform);
            copy.SetActive(false);
            pool.Add(copy);
        }
    }

    public GameObject Get(Vector3 position)
    {
        // Reuse the first copy that is currently hidden.
        foreach (GameObject copy in pool)
        {
            if (!copy.activeSelf)
            {
                copy.transform.position = position;
                copy.SetActive(true);
                return copy;
            }
        }

        // Every copy is in use.
        return null;
    }
}

    
Add this script to the prefab so each copy hides itself after two seconds:

    
using UnityEngine;

public class PooledObject : MonoBehaviour
{
    void OnEnable()
    {
        // Give the object back to the pool after two seconds.
        Invoke(nameof(ReturnToPool), 2f);
    }

    void ReturnToPool()
    {
        // Hide the object instead of destroying it.
        gameObject.SetActive(false);
    }
}

    
Add this script to an empty GameObject to test the pool:

    
using UnityEngine;

public class Spawner : MonoBehaviour
{
    // Drag the object with the SimplePool script here.
    public SimplePool pool;

    void Start()
    {
        // Ask the pool for an object once per second.
        InvokeRepeating(nameof(Spawn), 1f, 1f);
    }

    void Spawn()
    {
        // Place it at a random position near this object.
        pool.Get(transform.position + Random.insideUnitSphere * 3f);
    }
}

    
    
      
  1. Create a prefab, such as a small sphere, and add PooledObject to it.
    2. 
      
  2. Create an empty GameObject named Pool, add SimplePool and drag the prefab into its Prefab field.
    3. 
      
  3. Create another empty GameObject, add Spawner and drag Pool into its Pool field.
    4. 
      
  4. Enter Play Mode. Objects appear and disappear, but Pool always contains the same ten objects.
    5. 
    

    
Object pooling is mainly a performance technique. It does not replace state tracking or an inventory.

using UnityEngine;
using UnityEngine.InputSystem;

public class MiniMapToggle : MonoBehaviour
{
    // Drag the ToggleMap action from MenuControls into this field.
    public InputActionReference toggleMapAction;

    // Drag the mini-map Raw Image or its parent panel here.
    public GameObject miniMapDisplay;

    void OnEnable()
    {
        // Begin listening for the ToggleMap action.
        toggleMapAction.action.Enable();
    }

    void OnDisable()
    {
        // Stop listening when this component is disabled.
        toggleMapAction.action.Disable();
    }

    void Update()
    {
        // Check whether the ToggleMap action was pressed this frame.
        if (toggleMapAction.action.WasPressedThisFrame())
        {
            // Reverse the mini-map's current visibility.
            bool shouldBeVisible = !miniMapDisplay.activeSelf;

            // Show or hide the mini-map.
            miniMapDisplay.SetActive(shouldBeVisible);
        }
    }
}

Saving after quitting

    
Keep progress after the game closes, from a single saved number to a complete save file.

    
Application Variables and DontDestroyOnLoad reset when the game closes. To keep progress between play sessions, the information has to be saved.


    
Option A: Visual Scripting

    
Use a Saved Variable. It works like an Application Variable, but its value is kept after the game closes.

    
    
      
  1. Open the Variables window or Blackboard and select the Saved tab.
    2. 
      
  2. Create CollectedObjects there (Integer, starting value 0) instead of in the Application tab.
    3. 
      
  3. In the collectible and display graphs, set the scope of the Get and Set Variable nodes to Saved.
    4. 
      
  4. Collect some objects, stop Play Mode and press Play again. The number is still there.
    5. 
    

    
Unity stores Saved Variables in PlayerPrefs. They hold simple values such as numbers, text and lists of these, and they can’t refer to Unity objects like GameObjects or components.

    
To start fresh while testing, choose Edit → Clear All PlayerPrefs.


    
Option B: C#

    
Use PlayerPrefs. It saves simple values on the player’s computer under a name you choose. Add saving and loading to GameState:

    
// Replace Start and CollectObject in GameState, and add Save and Load.

void Start()
{
    // Load saved progress first, then display it.
    Load();
    UpdateDisplay();
}

public void CollectObject()
{
    collectedObjects++;

    // Save every time the value changes.
    Save();

    UpdateDisplay();
}

void Save()
{
    PlayerPrefs.SetInt("CollectedObjects", collectedObjects);
    PlayerPrefs.Save();
}

void Load()
{
    // The second value is used if nothing has been saved yet.
    collectedObjects = PlayerPrefs.GetInt("CollectedObjects", 0);
}

    
PlayerPrefs can only store an int, a float or a string. A list has to be turned into one string first:

    
// Save: turn the list into one string.
PlayerPrefs.SetString("Inventory", string.Join(",", inventory));

// Load: split the string back into a list.
string saved = PlayerPrefs.GetString("Inventory", "");
inventory = saved == "" ? new List<string>() : new List<string>(saved.Split(','));

    
To start fresh while testing, call PlayerPrefs.DeleteKey("CollectedObjects"), or PlayerPrefs.DeleteAll() to remove everything.


    
Where these methods stop

    
Saved Variables and PlayerPrefs suit a few simple values: a score, a setting, a counter. Joining a list into a string already feels awkward. A larger game needs a different approach.


    
Outlook: storing a more complex game progress

    
Real progress can include many items, quest stages, the current scene, the player’s position and the state of the world. The usual solution is a save file.

    
Separate what the game contains from what has changed. Prefabs, Scriptable Objects and scenes are part of the game and are not saved. Only the changes are saved: what the player owns, what has happened and where they are.

    
    
      
  1. Collect all progress in one plain data class marked [System.Serializable].
    2. 
      
  2. Convert it to JSON text with JsonUtility.ToJson.
    3. 
      
  3. Write the text to a file in Application.persistentDataPath.
    4. 
      
  4. When the game starts, read the file, rebuild the data with JsonUtility.FromJson and apply the values back to the game.
    5. 
    

    
using System.Collections.Generic;
using System.IO;
using UnityEngine;

// Plain data only: numbers, text, true/false values and lists.
// No GameObjects or components.
[System.Serializable]
public class SaveData
{
    public int version = 1;
    public string sceneName;
    public Vector3 playerPosition;
    public int collectedObjects;
    public List<string> inventory = new List<string>();
    public List<string> completedQuests = new List<string>();
}

public static class SaveSystem
{
    // A folder Unity provides for each player and platform.
    static string FilePath =>
        Path.Combine(Application.persistentDataPath, "save.json");

    public static void Save(SaveData data)
    {
        // Convert the data to readable JSON text and write it to a file.
        string json = JsonUtility.ToJson(data, true);
        File.WriteAllText(FilePath, json);
    }

    public static SaveData Load()
    {
        // Start fresh if there is no save file yet.
        if (!File.Exists(FilePath))
        {
            return new SaveData();
        }

        // Read the file and rebuild the data from the JSON text.
        string json = File.ReadAllText(FilePath);
        return JsonUtility.FromJson<SaveData>(json);
    }
}

    
Then connect it to the state you already track:

    
// Inside GameState: copy the current state into SaveData and save it.
SaveData data = new SaveData();
data.collectedObjects = collectedObjects;
data.inventory = new List<string>(inventory);
data.sceneName = SceneManager.GetActiveScene().name;
SaveSystem.Save(data);

// Later, load it and copy the values back into the game.
SaveData loaded = SaveSystem.Load();
collectedObjects = loaded.collectedObjects;
inventory = loaded.inventory;

    
Visual Scripting has no built-in file saving beyond Saved Variables. A common approach is a hybrid: keep SaveSystem in C# and call its Save and Load methods from a graph. After adding a new script you may need to select Regenerate Nodes in Project Settings → Visual Scripting so its methods appear.

    
Things to plan for a larger save system:

    
    
      
  • Save what changed, not whole scene objects. Give items, locations and events unique IDs so the save file can refer to them.
    • 
      
  • Store only an item’s ID or name in the save file. The Scriptable Object defines the rest.
    • 
      
  • Add a version number so older save files can be upgraded after you change the format.
    • 
      
  • Save at clear moments: checkpoints, scene changes and when the player quits.
    • 
      
  • Use one file per save slot, for example save1.json and save2.json.
    • 
      
  • Test loading with a missing file and with an old file.
    • 
      
  • JSON files are easy to read and edit. If cheating matters, encrypt the file or store progress on a server.
    • 
      
  • Bigger projects may use binary formats, a database, cloud saves or a ready-made save asset.
    • 
    

  


  

    
Best practices

    
    
      
  • Establish persistent objects in the first scene or as early as possible.
    • 
      
  • Keep persistent objects at the top level of the Hierarchy.
    • 
      
  • Make sure only one copy of each persistent manager exists.
    • 
      
  • Keep shared information in a clearly named object such as GameState.
    • 
      
  • Give important items, locations and events unique IDs.
    • 
      
  • Track information about an event instead of keeping every scene object alive.
    • 
      
  • Avoid persistent references to objects that disappear when a scene closes.
    • 
      
  • Use the Console while developing so you can see when values change.
    • 
      
  • Add a Canvas display when players also need to see the information.
    • 
      
  • Use Scriptable Objects to define reusable items and content.
    • 
      
  • Use object pooling for frequently reused objects.
    • 
      
  • Do not use object pooling as a replacement for state tracking.
    • 
      
  • Use DontDestroyOnLoad only for objects that genuinely need to survive.
    • 
      
  • Remember that Application Variables and DontDestroyOnLoad last only while the game is running.
    • 
      
  • Use Saved Variables or a separate save system if information must remain after the player quits.
