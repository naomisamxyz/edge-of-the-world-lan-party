ScriptableObjects

    
To track the state of objects or values like health across scenes in Unity, you must prevent the data from being destroyed when a new scene loads. Here are three standard ways to handle persistent state tracking, starting with the recommended one for shared data.

    
ScriptableObjects exist independently of any specific scene. You can save your health or inventory data inside a ScriptableObject asset, and any script in any scene can read or write to it.

    
using UnityEngine;

[CreateAssetMenu(fileName = "PlayerStats", menuName = "Stats/PlayerStats")]
public class PlayerStats : ScriptableObject
{
    public int health;
    public int maxHealth;
}

    
How to use: create the asset in your project files (Assets → Create → Stats → PlayerStats), then drag it into a slot on your scene scripts — a UI manager or player controller — to read and modify the shared data.

  


  

  

    
Don’t Destroy on Load

    
If you need an entire GameObject — a GameManager or AudioManager — to survive scene transitions, call Object.DontDestroyOnLoad.

    
using UnityEngine;

public class GameManager : MonoBehaviour
{
    public static GameManager Instance { get; private set; }
    public int playerHealth = 100;

    private void Awake()
    {
        // Enforce a Singleton pattern so duplicates aren't created when reloading scenes
        if (Instance != null && Instance != this)
        {
            Destroy(gameObject);
            return;
        }

        Instance = this;
        DontDestroyOnLoad(gameObject);
    }
}

    
How to use: access the health from any scene with GameManager.Instance.playerHealth.

  


  

  

    
PlayerPrefs

    
If you want the health value to persist not just across scenes, but also when the player closes and restarts the game, use PlayerPrefs.

    
// Saving the health value
PlayerPrefs.SetInt("PlayerHealth", 80);
PlayerPrefs.Save();

// Loading the health value (defaults to 100 if the key doesn't exist yet)
int currentHealth = PlayerPrefs.GetInt("PlayerHealth", 100);

  


  

  

    
Comparison

    

      

        
Direct comparison

        

          
ScriptableObjects
best for shared gameplay data, stats, and configurations. Does not persist after the game closes — resets on restart. Low setup complexity.

          
Don’t Destroy on Load
best for managers, audio players, and network controllers. Does not persist after the game closes — resets on restart. Medium setup complexity — requires singleton logic.

          
PlayerPrefs
best for high scores, settings, and basic save states. Persists after the game closes. Low setup complexity.
